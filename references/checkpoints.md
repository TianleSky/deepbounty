# 重点漏洞测试要点规范（DeepBounty 编号化，供矩阵点对点应答）

本文件是漏洞挖掘「重点漏洞类型」的**编号化测试要点**权威来源。挖掘时对适用的漏洞类型**逐要点执行**，并在参数漏洞矩阵条目的 `checkpoint_response` 字段**点对点应答**。

**如何应答（`checkpoint_response`）**：

- 结构为对象：`KEY` = 测试要点编号（如 `SQL001`），`VALUE` = **是否符合的声明 + 为符合做了哪些操作**。
- **必填条件**：当该条目 `vuln_type` 在本规范中有对应要点，且 `status ∈ {tested_not_found, doubtful, filtered}` 时**必填**；`found` / `not_applicable` 可空。
- **全覆盖（DeepBounty 硬要求）**：该类型编号集中**每个要点都必须有应答**；某要点确不适用时，在 `VALUE` 中声明「不适用及原因」，**禁止凭空省略**（修 tyang-skill2 漏答也过门）。
- 应答的 `KEY` 必须是该 `vuln_type` 对应前缀下的合法编号（见文末总表），门禁校验 KEY 越界与全覆盖。

> **机读单一事实源**：编号→漏洞类型的映射固化在 `scripts/common.py` 的 `VULN_CHECKPOINTS`。
> **两处一致性由 `checkpoint_gate.py` 双向自校验强制保证**（机读集有而本文没有、或本文有而机读集没有，都是硬错误）——修 tyang-skill2 "SQL004 在 md 有但机读集没有，答了反被判越界"事故。
> **分类型增量手册**：各漏洞类的 payload 族/判定逻辑/案例细节见 `vuln-recipes/<类型>.md`（14 家对标吸收），WAF 绕过见 `waf-bypass.md`——本文件只管「必答要点」，细节手册管「怎么打」。

## SQL — SQL 注入（generic）

| 编号   | 测试要点 |
| ------ | -------- |
| SQL001 | **必测防护规则**：以下每种类型至少测试3个不同的例子，检查其是否被过滤/拦截/替换/转义/放行，据实记入 `filter_probe`：<br />- **空白字符和注释符**：如`空格`、`#`、`/**/`、`-- `等<br />- **SQL常用关键字**：如AND、OR、SELECT、WHERE等<br />- **SQL常用符号**：`'`、`""`、`()`、`%`等 |
| SQL002 | **先判闭合再构造payload**：识别参数拼接上下文（`'...'` 字符串、`%...%` 的 LIKE、`(...)` 括号、数字型无引号、`ORDER BY` 等）针对性闭合，**严禁机械套用固定 payload** |
| SQL003 | **针对过滤规则定制payload**：至少尝试3种不同的绕过方式。关键字黑名单→大小写、内联注释、双写、等价函数/运算符等。探明空格被过滤/替换后→构造不带空格的payload 如使用无需空格的`&&`运算符代替AND、OR关键字或使用括号等。 |
| SQL004 | **充分尝试各注入类型（盲注强制）**：联合查询、报错注入、布尔盲注、时间盲注逐一尝试；**无回显时必做盲注**，不因单一类型无回显即判无注入。**时间盲注须 ≥5 次样本并与基线响应时间对比**（如基线 200ms，注入后 ≥5 次均 ≥5s 才算有时延信号），严禁单次抖动下结论。<br />**五条证据链纪律（吸收 strix）**：确认注入须齐备——①语法错误差异（`'` vs `''`）②tautology 差异（`OR 1=1` vs `OR 1=2`）③时序可复现 ④数据提取证明（版本/当前用户）⑤无害对照组正常；缺③④只能 `doubtful`/`filtered`，不许 `found`。 |

## XSS — 跨站脚本（generic）

| 编号   | 测试要点 |
| ------ | -------- |
| XSS001 | **黑名单绕过遍历**：遇标签/属性/事件黑名单时，遍历非黑名单标签（svg/video/audio/marquee/details 等）、事件（onerror/onload/ontoggle/onanimationstart 等）、协议与编码，**不因个别标签被拦即判安全**。 |
| XSS002 | **闭环验证输出上下文**：确认输入落到哪个页面哪个元素、是 `innerHTML` 还是 `textContent`、属性/JS/HTML 上下文；**存储型须到实际渲染页验证执行（跨 URL 也要验）**。 |

## CMDI — 命令注入（generic）

| 编号    | 测试要点 |
| ------- | -------- |
| CMDI001 | **探测分隔与拼接位**：在正常值中段注入 `;`、`|`、`&&`、反引号、`$()` 等，观察报错/时延/回显差异。 |
| CMDI002 | **无回显做带外/时延验证**：`ping -c` / `sleep` / `timeout` 制造时延，或 **OOB 带外（`oob_client.py` 取域名）**；确无带外通道且无时延差异记 `doubtful`。 |

## SSRF — 服务端请求伪造（generic）

| 编号    | 测试要点 |
| ------- | -------- |
| SSRF001 | **内网/本机/云元数据探测**：指向 `127.0.0.1`、内网段、`169.254.169.254`，对比时延·状态码·响应内容差异，判断服务端是否发起请求。 |
| SSRF002 | **协议与地址混淆绕过≥3 种**：`file://`/`gopher://`/`dict://` 协议、IP 进制/十进制/`@` 混淆、短域名、302 重定向、DNS rebinding。 |
| SSRF003 | **危害闭环**：读到内网/元数据内容或触发内网请求的证据；无带外与回显时以时延/报错差异佐证，确不可验记 `doubtful`。 |
| SSRF004 | **OOB 带外强制**：凡 SSRF 测试**必须用 `oob_client.py` 取唯一子域做带外确认**（interactsh 公共服）；有回显的也要补一次 OOB 坐实服务端出网。无 OOB 交互且无回显差异 → 不许记 tested_not_found，记 `doubtful`（修 tyang-skill2 SSRF≈0）。<br />**DNS-only 不算数（吸收 Agentic-Bug-Hunter triage 硬规则）**：仅 DNS 回调（egress 只放行 53 的常见情况）不足以提交——必须补 HTTP 回连或内网响应差异；云元数据须拿到 IAM 临时凭证才算 SSRF003 危害闭环。 |

## SSTI — 服务端模板注入（generic）

公开方法来自 PortSwigger SSTI 研究/Academy：明文上下文用数学表达式探测求值，再用差异探针与报错类名定引擎。指纹表与未知引擎流程见 [expression-engines.md](expression-engines.md)。**算出算术结果或引擎自报类名即可 `found`，不以系统命令执行为成立条件。**

| 编号    | 测试要点 |
| ------- | -------- |
| SSTI001 | **多族定界探测**：至少覆盖 `{{7*7}}`、`${7*7}`、`#{7*7}`、`<%= 7*7 %>`、`@(7*7)`；Java/Spring 视图再加 Thymeleaf 内联 `[[${7*7}]]`、FreeMarker `<#assign x=7*7>${x}`、Velocity `#set($x=7*7)$x`。用非常见乘积（如 `41*43=1763`）避免和页面数字撞车。应答须写清测了哪些定界、响应是原样回显还是求值。<br />**精确匹配纪律（吸收 Argus）**：求值判定必须**精确字符串匹配**运算结果（如响应含 `1763` 子串），且该数字不得出现在对照组（无害输入）响应中——防止页面既有数字造成假阳性。 |
| SSTI002 | **定引擎，禁止一锤定音**：`{{7*'7'}}` 分 Jinja2（`7777777`）与 Twig（`49`）；`${}` 命中后继续分 FreeMarker / Velocity / Thymeleaf / EL，不得只凭一次 `49` 写成「就是某某」。无效语法 polyglot 的堆栈类名须摘录。 |
| SSTI003 | **未知引擎发现（表外也要测）**：报错类名、模板后缀、HTML 注释里的引擎 banner 不在 [expression-engines.md](expression-engines.md) 表中时，用该类名/新定界补一条算术探针；任意一对定界让算术生效即记 `found`。**禁止**因不在清单中就 `tested_not_found`。 |
| SSTI004 | **过滤与无回显**：定界被剥/拦时至少 3 种换皮（URL 编码、定界内空格、拆分左右定界）；无回显对比时延/带外。拦死但仍有模板解析报错记 `filtered`；原样回显且无解析差异记 `tested_not_found`（须声明已测的定界族）。 |

## ELI — 表达式注入（generic，Java EL / OGNL / SpEL / MVEL / JEXL 等）

与 SSTI 可同时适用（`${7*7}` 两族都可能）。**求值成立即可 `found`，不要求、不构造系统命令执行。** 指纹见 [expression-engines.md](expression-engines.md)。

| 编号   | 测试要点 |
| ------ | -------- |
| ELI001 | **Java 表达式定界全覆盖**：`${7*7}`（Unified EL / SpEL / 部分 OGNL）、`#{7*7}`（JSF 延迟 EL / 部分 SpEL）、`%{7*7}`（OGNL/Struts2）。框架痕迹只作先验，仍须实打探针。 |
| ELI002 | **分种识别（无命令执行）**：SpEL 独有 `T(java.lang.Math).abs(-7)`→`7`；Unified EL 无 `T()`；OGNL 看 `%{}` 与 `ognl.OgnlException`；MVEL/JEXL 以类名为准。认不出引擎但已求值仍 `found`。 |
| ELI003 | **未知表达式语言发现**：堆栈出现未收录的解析器类名时，记下全类名并按其文档补算术探针；规则引擎/工作流字段即使无定界，也要试「整段参数=`41*43`」是否变成 `1763`。 |
| ELI004 | **过滤与双族交叉**：`${` `#` `%` 被拦时换编码/拆分/另一套定界；Java 站即使已确认 FreeMarker/Thymeleaf，仍须抽测 OGNL `%{}` 与 SpEL `T(java.lang.Math)`。 |

## AUTHZ — 越权/未授权访问（business_logic）

| 编号     | 测试要点 |
| -------- | -------- |
| AUTHZ001 | **越权前正向确认会话角色**：测试前先用该会话成功访问"本角色专属且需登录"的接口并拿到本人数据，确认会话确以目标角色在线；应答须回填用何请求确认、会话是否有效及其角色结果。 |
| AUTHZ002 | **完整跟踪跳转再判权限**：遇 3xx/302 严禁据状态码直接判"已拦截/无权限"，必须跟踪到跳转后的最终页面/响应体（落到登录页=拦截；落到目标数据=越权成立）。 |
| AUTHZ003 | **以服务端数据差异坐实**：越权成立须以读到/改到他人或更高权限的真实数据为证，不能仅根据响应状态码不同判定。 |
| AUTHZ004 | **双账号交叉 diff（DeepBounty 强制）**：水平越权必须用 attacker/victim 双账号交叉访问**同一对象 ID** 做响应 diff（attacker 拿 victim 的订单/资料 ID 请求，对比与 victim 自己请求的响应一致性）；无双账号时该叶子记 `blocked`（cred_gate authz_blocked），**禁止记 tested_not_found**。应答须写明两账号 cred_id 与 diff 结论。<br />**无效 id 基线（吸收 Argus，`authz_probe.py` 已机读化）**：换 id 前先发不存在的 id（如 `0`/`99999999999`）——无效 id 也返回 200+数据 → 公开资源/兜底响应，**不是 IDOR**。<br />**写/删/改越权的无害证法（移植 AutoHunter write_proof 五分类，详见 [vuln-recipes/authz.md](vuln-recipes/authz.md)）**：只认四种强形态——哨兵闭环（自建 `SRC_TEST_<rand>` 增改删+旁路回读 before→after）/ 鉴权对照（未登录 401↔登录 200）/ 幂等回写原值（affectedRows≥1 且值未变）/ 旁路回读；只有成功文案或 `data:0` 为弱形态，evidence_gate 复核级打回。**无限制原则**：写/删/改可对真实数据验证，证据仍须闭环（before→after 或旁路回读），不能只贴成功文案。 |

## RACE — 并发/竞态 TOCTOU（business_logic）

| 编号    | 测试要点 |
| ------- | -------- |
| RACE001 | **识别 check-then-act 写操作**：库存/余额/限领/扣减/状态流转等「先查后写」的操作点。 |
| RACE002 | **构造未消费新包高并发发起**：不能重放已消费包；须**新造请求**并高并发，验超卖/超领/双花/越限。应答时必须回复未消费新包的关键特征（如sign）和并发启动前 {urlid}.log 中没有 grep 到该特征的证据。 |
| RACE003 | **以服务端状态差异坐实**：库存/余额/领取记录的前后对比证据，而非仅「响应成功」。<br />**串行对照组（吸收 strix 黄金判定）**：「串行拒绝、并发成功」——对照组串行发 N 次仅 1 次成功（业务限制生效），实验组并发发 N 次 >1 次成功（限制被绕过）；两组结果同记，缺对照组不算坐实。 |

## SMS — 验证码/短信绕过（business_logic）

| 编号   | 测试要点 |
| ------ | -------- |
| SMS001 | **置空校验**：验证码/短信码置空时后端是否仍校验。 |
